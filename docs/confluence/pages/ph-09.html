PH09-S01 · Versioned market profiles and instrument kinds behind an admission checklist

Positive

  • Market profiles and instrument kinds are versioned contracts covering venue, calendar, currency and quote unit, dual-listing mappings, rights, history depth, delay and budget.

  • Each extension carries its own contract tests, point-in-time replay, shadow evidence and the owner's activation approval before any listing in it becomes eligible.

  • A market or kind that needs new handler code ships only as tested code in this repository through a reviewed release.

  • Deactivating an extension rolls its version pointer back and keeps its history and past forecasts.

Negative

  • A chat proposal (PH05-S11) cannot add a market whose profile has not been admitted.

  • No extension implies a budget increase: its credits and cash are checked against the £100 ceiling before activation, and a source that needs a higher tier waits for its own owner decision.

  • No mainland China, Taiwan, Hong Kong or continental Europe listing is eligible in the first release.

Recovery

  • A failed activation leaves the extension inactive; withdrawn rights deactivate it and keep its history.

PH09-S02 · Dated theme membership that separates labels from measured exposure

Positive

  • Theme membership is many-to-many with effective dates and sources, versioned on every change.

  • A marketing label is distinguished from a measured economic exposure.

  • Themes compare with peers, benchmarks and the overlap with current holdings, computed by code.

Negative

  • Historical theme studies use historical constituents, never today's list.

  • A label alone is never counted as exposure.

Recovery

  • A corrected membership is a new version, and every study records the membership version it used.

PH09-S03 · Bounded screening beyond the curated universe, inside the approved budget

Positive

  • Code runs a batched daily quantitative screen; Claude (Haiku, batched) writes short explanations for a bounded shortlist only.

  • A workload plan states the data credits, AWS compute and Claude cost before the owner approves any expansion.

  • Any expansion beyond the curated universe needs the owner's approval and a recosting.

Negative

  • The universe never grows silently, and no Claude call ranks or scores a listing.

  • A scan overrun stops at the Claude cap.

Recovery

  • A failed screen keeps the previous shortlist with its date.

PH09-S04 · Admission for new features, model families and horizons

Positive

  • Feature sets, model adapters, forecast tasks, strategies, agent manifests and evaluation packs are versioned, and a capability matrix says what each version supports.

  • New computation needs tested trusted code, resource costing within the campaign ceilings (POLICY-008), ablation and matured or shadow evidence (8 scored weeks), then the owner's promotion.

  • A compatibility suite runs before admission.

Negative

  • No code or plugin is downloaded at runtime, and no model, tool or budget expands by itself.

  • A new agent route needs its manifest and evaluation suite (PH05-S06, PH05-S13) before it runs.

Recovery

  • A rejected or rolled-back extension keeps its history, and the scope reverts to the previous approved version.

PH09-S05 · Optional versioned file exchange with mypaisa-agent

Positive

  • There is no shared live database and no required MA API.

  • An optional export or import uses an approved, versioned file contract, and an import is reconciled and goes through PH-01's import flow and the owner's approval.

Negative

  • Nothing is exchanged until the owner approves a file contract (IR-02).

  • No MA page, issue, source or runtime is changed by this story.

Recovery

  • A failed or rejected import follows PH-01's recovery: nothing is committed, and the file stays in quarantine.

PH09-S06 · Retirement boundary for MA's forecaster: parity, history and an explicit cutover record

Positive

  • Before any retirement, the MA source, code and runtime inventory is refreshed, and agreed parity, history preservation and recovery are proved.

  • The cutover scope is a separate decision record the owner approves.

  • MA's rules, tracking and XIRR remain.

Negative

  • This plan and its story mapping authorise no change to MA.

  • There is no automatic migration and no DNS handover.

Recovery

  • If parity or history checks fail, there is no cutover and MA stays as it is.
