Acceptance

PH01-S01 · Owner and environment scope on every import and ledger path

Positive

  • The API, extraction workers, source access and the controlled writer derive owner and environment from server authentication and recheck them at every read, write and account mapping; no client field or file content chooses them.

  • A dev request naming a prod owner or account, or a document carrying "approved: true", publishes nothing and reads nothing from prod, and a privacy-safe denial is audited (FIN-AC-04).

  • Synthetic fixtures carry is_synthetic in their ScopeEnvelope and load only into dev; a fixture load aimed at prod is refused before any write.

Negative

  • No broker trading credential, order path or execution endpoint exists in the import or ledger code or configuration.

  • Signed source links, raw extracted fields, prompts, PDF passwords, account numbers and holding values never appear in general logs, traces, metrics or Web Push previews.

  • A worker resumed after a durable wait does not reuse a scope cached before the wait; it rechecks before acting.

Recovery

  • After a denied cross-scope request no partial record, staged chunk or cache entry is left in either environment, and the next correctly scoped request succeeds unchanged.

  • If the redaction filter cannot load, the service withholds the affected telemetry rather than emitting unredacted values.

PH01-S02 · Bounded work and cost for import processing

Positive

  • Each extraction job reserves its file size, wall time, Claude tokens and concurrency slot before it starts, and records actual usage against that reservation exactly once, even when retried.

  • A Claude extraction call is admitted only when the shared cost admission confirms covered credit inside the Claude and evaluations allocation of £15 a month (COST-Q1); otherwise the job pauses with a visible reason.

  • Import activity appears in the main per-environment cost view, linked by import id, from cached or scheduled collectors with their lag stated.

Negative

  • No paid billing or usage API is called on a page refresh.

  • Unknown or unverifiable credit pauses the uncovered model call; there is no silent paid fallback.

  • A retried job cannot reserve a second budget for the same work item; usage accounting is idempotent on the job and attempt id.

Recovery

  • After a crash an expired reservation is reconciled against recorded usage, and the job resumes or stops under its original budget, never a fresh one.

  • A paused job resumes from its last checkpoint once credit is confirmed, without rerunning completed deterministic steps.

PH01-S03 · Owner-scoped accounts and listing identities

Positive

  • Issuer, security, share class, listing and provider alias are separate records; CNX1 on XLON in GBP and CNDX on XLON in USD keep separate listings while sharing ISIN IE00B53SZB19 (FIN-AC-03).

  • A provider ticker rename adds a new effective-dated alias version without rewriting history that used the old alias.

  • An account records its institution alias, jurisdiction, wrapper label and permitted settlement currencies as source-backed labels, with tax_logic_applied false.

Negative

  • An ISIN or a name that matches more than one listing yields candidates for the owner to choose; the system never picks one.

  • No tax rule is inferred from a wrapper label such as ISA or SIPP, and no broker credential or full account number is stored, only a protected reference token.

  • Fixtures use real public identifiers (UK-VOD-XLON-GBX, US-AAPL-XNAS-USD, IN-RELIANCE-XNSE-INR) with fictional balances; the owner's actual holdings are not loaded.

Recovery

  • An abandoned listing choice leaves the candidates open and the dependent rows blocked; choosing later creates a new version and the earlier state stays in history.

  • Correcting a wrongly created account or listing creates a new version with an audit link; the earlier version stays readable.

PH01-S04 · Business audit lineage and integrity checks

Positive

  • Every ledger publication, correction, reversal, mapping choice, approval, denial and deletion writes an AuditEvidence record with actor, operation, targets, source refs, approval id and commit id, in the same logical commit as the change.

  • Business audit is unsampled and kept for the account's lifetime (POLICY-010), separate from operational telemetry kept 14 days for logs, 30 days for rich traces and 90 days for run summaries.

  • The question "who changed this fee, from which document, what did I approve, and which forecasts used it" resolves through AuditQuery with bounded pagination and no general table scan.

Negative

  • A hash chain alone is never described as tamper-proof; integrity_claim stays at the level the approved anchoring design supports.

  • A financial change without its audit record is never acknowledged as committed.

  • Audit records hold references, never document content, prompts, tokens or holding values.

Recovery

  • A synthetic missing or altered audit event is detected by the integrity check and reported as an integrity failure naming the affected range.

  • If an index lags, the query falls back to authoritative manifest joins and returns the complete lineage, or reports INTEGRITY_INCOMPLETE rather than a partial answer.

PH01-S05 · Original files kept, deleted and restored without resurrection

Positive

  • Each original has a renewable 24-month retention with owner extension and owner deletion; there is no automatic expiry deletion and no irreversible Object Lock.

  • An owner deletion removes the original and its derived text, records a tombstone and an audit event, and later evidence joins show the source as deleted.

  • Ledger events that came from a deleted original remain, marked evidence-unavailable, rather than disappearing (POLICY-010).

Negative

  • A backup restore cannot resurrect a deleted original or its derived text; tombstones are applied before restored content is readable.

  • Deletion never removes ledger history or audit records; it removes content only.

  • An orphaned object is not deleted automatically; the owner records what happens to each orphan, and it follows that recorded disposition. ADM-20, 5 November 2026 (MP-184): the owner picked "Code cancels, orphans yours" (by the owner's words in chat, "for the remaining pick up recommended options").

Recovery

  • A deletion interrupted midway resumes from its tombstone and reports any copy it could not yet remove.

  • An isolated restore exercise followed by tombstone reapplication leaves the deleted content unreadable.

PH01-S06 · Private validated upload intake

Positive

  • Byte size, magic type, checksum, archive, page, pixel and runtime checks run, and the file is quarantined, before any extraction starts.

  • The original bytes, their storage version and a SourceReceipt exist before processing; the source moves received, quarantined, extracting only through the defined transitions.

  • A rejected upload shows the owner a visible reason, such as an unsupported type or too many pages.

Negative

  • An object-created notification never marks an import committed or creates a ledger effect.

  • Upload authorisation is scoped to owner, environment and one upload intent, is short-lived, and single use is enforced by the app rather than assumed from a signed URL.

  • Originals are never public. MP40-Q1, 5 November 2026 (MP-184): the owner picked "Set from your real statements" (by the owner's words in chat, "for the remaining pick up recommended options"). The option read: "Oversized files stay held as drawn, and the four limits are set from your largest real statements, with a margin, when they arrive." Until those limits are set from the owner's real statements and approved, no limit value is treated as approved, an oversized file is held for review, and the intake policy version marks unapproved values.

Recovery

  • Repeated or out-of-order notifications resolve to the same receipt; an object without a receipt is quarantined as an orphan, and a receipt with a missing or wrong object is blocked (FIN-AC-15). The owner records what happens to each orphan. ADM-20, 5 November 2026 (MP-184): the owner picked "Code cancels, orphans yours" (by the owner's words in chat, "for the remaining pick up recommended options").

  • A failed validation needs a new processing revision; the original bytes are never replaced.

PH01-S07 · Deterministic parsers for CSV, Excel and text PDFs

Positive

  • Supported CSV, Excel and text-PDF layouts in the versioned layout register produce DraftRows whose every field records the raw literal, the normalised value, the parser and schema version, and a row and column, sheet and cell, or page and region locator.

  • Missing data stays missing: an absent fee or date is recorded as absent, never as zero or a default.

  • Generic synthetic fixtures are labelled generic and kept distinct from layouts validated on real broker samples.

  • A PDF unlocked in the local step on the owner's device arrives as an unlocked copy through the validated upload intake (PH01-S06) and is parsed like any other text PDF.

  • This story also builds the local PDF unlock step: the owner types the password in a step on their device, which opens the PDF there and uploads the unlocked copy. MP203-07, 24 November 2026 (MP-203): the owner picked "Widen three existing stories" (pressed on the page). The option read: "MP-47 gains the unlock step, MP-107 the factsheet reader and MP-163 the two builds." The password is never logged or sent to a model, and it never leaves the device and is never stored (proposed). The step is built in the web app here; the Apple app's step arrives with the Apple journeys in PH-07 (PH07-S02, MP-168) (proposed). How a browser opens and re-saves an encrypted PDF on the device is unverified until a test proves it (proposed).

Negative

  • Cell formulas, macros, links and embedded text are data only; no formula, script or network call runs to import a workbook, and instruction-like text changes nothing.

  • An unsupported layout is reported as unsupported with the evidence of why, never guessed into rows.

  • An encrypted PDF is held as needing unlock and is not parsed; no password is logged or sent to a model. MP40-Q2, 5 November 2026 (MP-184): the owner picked "Local unlock step" (pressed on the page). The option read: "You type the password in a step on your device, which opens the PDF there and uploads the unlocked copy." The password stays on the owner's device and never reaches MP's servers (proposed).

  • The unlock step never sends the password or the locked original to MP's servers, and keeps neither after the step closes (proposed).

Recovery

  • A parser failure moves the source to extraction_failed with a retry disposition; reprocessing with a new parser version creates a new draft revision and keeps the old one.

  • A crash mid-parse leaves no partial draft visible; a rerun produces the same rows for the same bytes and parser version.

  • A wrong password opens nothing and uploads nothing; the step says the password did not open the file and lets the owner try again (proposed).

  • Cancelling the unlock step uploads nothing and leaves the file as it was (proposed).

  • A file that stays locked (an encryption the step cannot open, or a password the owner does not have) uploads nothing; an encrypted PDF that reached intake stays as needing unlock, with its reason, and is not parsed (proposed).

PH01-S08 · Tool-free Claude extraction for scanned PDFs and screenshots

Positive

  • The extraction route (Haiku 5.5 under ARC-06b) runs with no tools and no write authority, inside its reserved token and time budget, and returns a schema-validated typed proposal.

  • Every field carries the page and region or image region it came from, the model id, the prompt and schema versions and a confidence; a field the model cannot read is absent, not guessed.

  • Output that fails schema validation is refused and the source moves to extraction_failed with a reason.

Negative

  • Instructions inside a document, such as "approve this", have no effect; a hostile-text fixture is flagged and never approved.

  • Claude output is a draft only and cannot become ledger truth without the owner's exact approval.

  • No password or account number is sent to the model, and only the document pages the route needs leave MP.

Recovery

  • A timed-out or refused model call is retried within the same reservation and a bounded number of attempts, then stops with a visible reason; it never retries under a new budget.

  • A model or prompt version change reprocesses into a new draft revision; the old revision stays for comparison.

PH01-S09 · Manual entry through the same import pipeline

Positive

  • A manual entry creates a SourceReceipt with intake_method manual, and DraftRows whose evidence points to the entered field and entry time.

  • Manual rows pass through the same matching, normalisation, duplicate, preview and approval steps as file rows.

  • A manual snapshot (units and value, no history) is recorded as an observation, not as invented purchase transactions.

Negative

  • A manual entry cannot skip preview or approval and cannot write the ledger directly.

  • An entry missing a required field such as currency, date or units is refused with the field named; nothing is defaulted.

Recovery

  • An unsent manual draft is kept so the owner can resume it, and a duplicate submit of the same entry resolves to the same draft.

PH01-S10 · Instrument and account matching

Positive

  • Matching uses verified identifiers with venue, currency and share-class context, and records the confidence and evidence of each match.

  • An unknown or ambiguous match blocks only the rows that depend on it; choosing a mapping creates a new draft revision.

  • A saved mapping or layout template is versioned, scoped to the owner and environment, and shown when it is reused.

Negative

  • A similar ticker or name never turns one listing into another silently; reusing a mapping that no longer fits its context is flagged, not applied.

  • A factsheet can describe a candidate instrument but cannot create units, cost or purchase history for the owner.

Recovery

  • Undoing a mapping choice creates another draft revision and restores the blocked state of the dependent rows; earlier revisions stay.

  • If the listing catalogue changes after mapping, the draft is marked stale and rematched before approval.

PH01-S11 · Exact normalisation of money, dates and events

Positive

  • 12000 GBX for 2 units with a 1 GBP fee normalises once to 120 GBP a unit and -241 GBP net, keeping the raw literal and factor (FIN-AC-01).

  • Booked net amounts, unit prices, fees, withholding, and FX execution versus reference rates stay distinct and reconcile exactly after declared unit conversion; a one-minor-unit difference is flagged.

  • Trade, settlement, observed, available and recorded times keep their meanings, and a date-only input stays date-only.

  • Each event has validated cash and quantity legs: exposure from the trade date, settlement tracked separately (POLICY-007).

Negative

  • Normalising an amount already in GBP with the GBX factor is refused, and unknown fees or currencies are never set to zero or a default.

  • NaN, exponent strings, negative zero and values beyond the precision bounds are refused with field evidence (FIN-AC-02).

  • Transfers, FX and splits keep their economic boundaries, unlike units are never summed, and a missing settlement date is not invented.

Recovery

  • A normalisation failure marks the row needs_resolution with the reason; fixing the source value creates a new draft revision.

  • A changed normalisation policy version reruns normalisation into a new revision and invalidates any pending approval.

PH01-S12 · Business deduplication and replay-safe identity

Positive

  • File, source-row and economic-event identities are separate, scoped and versioned.

  • Retrying the same bytes, or the same broker event in another format, has one effect per economic id (FIN-AC-07).

  • Two genuine same-day, same-amount trades with distinct stable references stay two events (L1-E05).

Negative

  • A collision with no reference evidence goes to duplicate review; it is never discarded or inserted automatically.

  • Reprocessing with a new parser cannot bypass economic deduplication; a changed fact becomes a correction proposal, not a second original trade.

Recovery

  • A published operation retried after 20 minutes or after a service-token restart returns the same receipt and revision, and the same key with a changed payload returns IDEMPOTENCY_CONFLICT (FIN-AC-08).

  • An open duplicate review keeps the affected rows pending and visible; deciding later creates a new draft revision.

PH01-S13 · Import preview, guided edits and explicit group selection

Positive

  • The preview shows every accepted, blocked, duplicate and excluded row, the account and listing mappings, before and after values, errors and which measures each change affects.

  • Any edit, exclusion, mapping or parser change creates a new draft revision with a new canonical hash and invalidates any earlier approval (FIN-AC-06).

  • The owner may select explicitly reviewed, complete transaction groups; each keeps its cash, fee and dependent entries together, and unresolved rows stay pending and visible (POLICY-005).

Negative

  • No row is dropped silently; a subset holding a sale without its history, or an unresolved transfer shown as income, is refused.

  • Document content cannot approve, select or edit rows.

  • An approval made on an older hash cannot apply to the new revision.

Recovery

  • The owner can leave and resume a draft; a draft whose expected ledger revision is now stale is marked stale and needs a refreshed preview (L1-E09).

  • Cancel moves the draft to cancelled without touching the ledger; the original source stays.

PH01-S14 · Exact owner approval bound to the preview

Positive

  • An approval binds owner, environment, operation, draft revision, canonical payload hash, selected-rows hash, expected ledger revision, assurance policy version and an expiry 15 minutes after approval (POLICY-001).

  • Approval needs a server-verified sign-in fresh enough for a sensitive action; otherwise the owner is asked to step up.

  • Revoking or cancelling an approval before commit submission stops it from activating; any live signed-in session can revoke at once, and a signed-out device signs in first as usual. OWN-16, 5 November 2026 (MP-184): the owner picked "An open session is enough" (by the owner's words in chat, "for the remaining pick up recommended options"). The option read: "Any live signed-in session can revoke at once, and a signed-out device signs in first as usual."

Negative

  • A matching hash alone, a local Face ID unlock or an open session alone cannot authenticate an approval.

  • An approval for a different owner, environment, revision or payload is refused, and confirmation text inside a document never stands in for owner approval.

  • At or after expires_at the writer refuses to start the commit (FIN-AC-13).

Recovery

  • An expired approval on an unchanged payload is renewed by a fresh approval; a changed payload needs a new draft and a new approval.

  • A double tap on approve yields one approval record.

PH01-S15 · Atomic visible commit through the controlled writer

Positive

  • A commit advances the ledger head once, publishes the manifest, finalises the receipt, consumes the approval and appends the audit and one publication pointer in one bounded transaction (FIN-AC-09).

  • A large import stages immutable chunks under a fence, seals with verified counts and digest, and becomes visible only at activation; readers see the old revision until then (FIN-AC-11).

  • Every transaction is preflighted on action count, item size and aggregate bytes, audit and metadata included, before submission (FIN-AC-10).

Negative

  • Staged, failed or cancelled work is invisible to every reader, projection, agent and export.

  • A stale fence cannot write a chunk, seal or publish, and two commits racing on one revision have one winner (FIN-AC-12).

  • A commit never publishes chunk by chunk, and an S3 object never commits a portfolio.

Recovery

  • A lost response is outcome_unknown: the writer reads the receipt, manifest and head and retries only the same operation, with no compensating import (FIN-AC-14).

  • A crash after any chunk, during sealing, after complete or after activation resumes or cancels without partial visibility, and a retry returns the same receipt.

PH01-S16 · Deterministic ledger replay and versioned projections

Positive

  • Rebuilding from the same committed events and policy versions gives identical projections; caches are never financial truth.

  • Trade, settlement and transfer ordering is explicit, with trade-date exposure and settled and unsettled cash kept apart, never counted twice (POLICY-007).

  • Every read pins a strongly read published head, and a pinned older revision stays valid while a newer one publishes.

Negative

  • Failed, staged or superseded work never appears in holdings, measures, agent context or read APIs.

  • An unresolved same-date ordering tie, negative balance, oversell, or margin or short position is surfaced as an exception that blocks dependent measures, never guessed (FIN-AC-24).

  • Dividends and fees are counted once (FIN-AC-22).

Recovery

  • A projection that differs from a rebuild is discarded and rebuilt from events, and the difference is reported.

  • A later complete history becomes a new baseline generation only through an approved rebase, never adding the same units twice.

PH01-S17 · Cash, units and valuation reconciliation

Positive

  • Differences between statements and the ledger in cash, units, fees, FX, dates and coverage are classified with both source and derived values.

  • A valuation total carries price and FX times, sources and quality; an unpriced holding gives a known subtotal and a visible missing part, not a complete total (L1-E08, FIN-AC-25).

  • An owner resolution records its reason and source, and a change to financial facts goes through a correction with a new revision.

Negative

  • No plug trade or silent overwrite clears an unexplained difference.

  • A price or FX rate with unknown use rights, or older than the freshness policy allows, is not used in a total, and the reason is shown. OWN-07, 5 November 2026 (MP-184): the owner picked "Approve the proposed limits now" (by the owner's words in chat, "for the remaining pick up recommended options"). The option read: "A quote is fresh to its interval end plus its delay plus 5 minutes. A close is fresh to the next expected close plus a grace. A fund price is overdue 60 minutes after its deadline. FX may be 24 hours old." The close grace has no figure yet (DATA-DEC-02).

  • Funds valued from the owner's statements (DATA-DEC-07, DATA-DEC-08) carry their statement date and are never shown as daily prices.

Recovery

  • An open difference stays open and visible across sessions, and reconciliation reruns when new evidence arrives. A small open cash difference leaves the account's return showing and flagged; above a limit the owner approves, the return is withheld. OWN-31, 5 November 2026 (MP-184): the owner picked "Withhold only if material" (by the owner's words in chat, "for the remaining pick up recommended options"). The option read: "A small difference leaves the return showing and flagged. Above a limit you approve, the return is withheld." That limit is not set yet; it is set with the reconciliation limits (FIN-OD-01).

  • When a missing price arrives later, the total is recomputed as a new result and the earlier partial result remains.

PH01-S18 · Corrections, reversal and baseline rebase

Positive

  • A correction commits a linked inverse of every original leg together with its replacement, and the original persists (FIN-AC-16: cash 798, units 2).

  • An import-level reversal is its own preview and approval, and dependent later events and observations are checked first (FIN-AC-17).

  • When a later upload fills history behind a snapshot, a versioned rebuild proposal shows the reconciliation and performance effects; after exact approval the opening baseline is retired at a cutover in a new generation, two units and not four (POLICY-012). A rebuild can be approved only when statements cover every unit, and a partial one stays held and visible. OWN-19, 5 November 2026 (MP-184): the owner picked "Whole history only" (by the owner's words in chat, "for the remaining pick up recommended options"). The option read: "A rebuild can be approved only when statements cover every unit. A part one stays held and visible."

Negative

  • A bulk delete cannot leave impossible quantities or remove audit history; an inconsistent reversal is refused unless its dependent corrections are approved together.

  • Issued forecasts and measures keep their original input revisions; later knowledge is not backdated into them.

  • Two corrections against the same original revision cannot both win.

Recovery

  • A repeated correction or reversal request returns the same receipt and does not reapply its effects.

  • A rebuild proposal that expires or loses to a newer revision is refreshed and approved again.

PH01-S19 · Per-measure sufficiency and labelled analytical cost basis

Positive

  • Each measure (valuation, basis, gain, return) has its own status: available, partial, unavailable, ambiguous, nonconvergent or integrity_failed, with reasons, set before any wording.

  • A snapshot of two units worth INR 200 with unknown history keeps its valuation while basis loss and return are unavailable (FIN-AC-25, L1-E03).

  • Where history supports it and no usable broker basis exists, an analytical FIFO basis is computed and labelled analytical and not tax basis, and broker figures keep their provenance (POLICY-009).

Negative

  • Missing purchases, fees or FX are never filled with fabricated transactions or a zero return.

  • The analytical basis never overwrites or relabels a broker figure.

Recovery

  • A failed calculation records integrity_failed with its reason and is retried on the next projection; no partial value is shown as complete.

  • When missing history arrives through a rebase, statuses are recomputed as new results and earlier results stay.

PH01-S20 · Money-weighted return (XIRR) for holdings, accounts and the portfolio

Positive

  • Holding, account and portfolio XIRR each use their own flow boundary, dated signs, a terminal valuation after same-day events and one currency; at portfolio scope internal trades, dividends and transfers are not external contributions (FIN-AC-18, L1-E06).

  • An exact 365-day 100 to 110 schedule gives 10% with zero NPV residual, and [-100, 230, -132] over 730 days returns both 10% and 20% roots with a null headline and ambiguous status (FIN-AC-19).

  • GBP results use dated booked GBP or dated reference FX labelled estimated, and show local, FX and interaction parts (FIN-AC-21).

Negative

  • All-zero, one-sign, same-day-only, unknown-date and nonconventional schedules return a specific unavailable, ambiguous or nonconvergent status, never NaN or zero (FIN-AC-20).

PH01-S21 · Scoped, paginated portfolio and import reads at a pinned revision

Positive

  • Reads serve owner, account, listing, date and status access patterns with a version, a cursor bound to the pinned ledger revision, and quality metadata.

  • Each response states the ledger revision, valuation cutoff and source ages it was built from.

  • Read-only agent tools return the same committed revision and evidence ids as the app.

Negative

  • No default read performs an unbounded table scan.

  • A model summary or a notification is never a source of figures; reads come only from published projections.

  • Private values are returned only to the authenticated owner in scope.

Recovery

  • A cursor whose revision has been superseded keeps returning the pinned revision until the client asks for the new one.

  • Missing expected items return INTEGRITY_INCOMPLETE, not a partial success.

PH01-S22 · Import progress notices with reconnect recovery

Positive

  • Import progress (received, quarantined, extracting, review ready, committed, failed) is sent as short SSE notices carrying only event id, type, time and resource reference.

  • After a reconnect the client resumes from the last event id where it can and always re-reads the durable import and receipt.

  • Notices are delivered at least once with stable message ids and consumer deduplication.

Negative

  • A notice never carries holdings, document content, credentials or provider payloads, and never stands in for commit truth.

  • Reconnecting or replaying a notice never repeats a mutation.

  • The starter's unauthenticated volatile SSE is not claimed as production evidence.

Recovery

  • After a gap the client refetches durable state and shows the true status.

  • A failed delivery is retried through DeliveryState without touching sealed intents.

PH01-S24 · Phase acceptance with synthetic examples and fault injection

PH01-S26 · Owner data export pinned to one ledger revision

Positive

  • An export pins one published ledger revision, its schema versions, as-of time, provenance and the FIN-HASH-1 root, so the same request against the same revision gives the same content (FIN-AC-29).

  • The owner gets a private download link that can start a download for one hour (POLICY-011); after expiry a new authenticated request issues a new link.

  • Creating, downloading and deleting an export are each audited with the owner, environment and revision.

Negative

  • An export never mixes two revisions: a revision published during the export does not change its content.

  • No public object URL is created, and an expired or revoked link starts no download.

  • Another owner or environment cannot request, see or download the export, and deleted evidence is not resurrected into it.

Recovery

  • An export interrupted part-way leaves no downloadable partial file; retrying with the same idempotency key resumes or restarts it without a duplicate.

  • A link that expires mid-download lets the transfer in progress finish but issues no new start without a fresh authenticated request.
